## Direct assignment after a phone agreement

Agreed requirement: an admin may assign an active worker from the same agency to one or several Care Slots even when that worker has not expressed interest in the app. Worker interest remains useful information, not a prerequisite for an office-arranged assignment.

Implemented and locally tested October 16, 2026; hosted rollout remains pending. See [implementation and verification](../backend/DIRECT_ASSIGNMENT.md).

Implemented journey:

1. From client Weekly care need → **Review coverage**, or Care requests, choose a worker for each uncovered slot.
2. Choose an active agency worker in each slot's dropdown: **Interested in this slot** comes first, followed by **Other active workers**. The separate **Interested workers** tab shows responses and notes; both tabs retain the same draft selections. There is no separate worker search or interest toggle. The review shows availability, conflicts, scheduled hours and blocking reasons for selected workers.
3. Select one or several slots and a start date. For workers without interest, confirm that coverage was arranged with them. Assignment history records `admin_arranged`, approver and time; no worker interest is created. Internal phone notes are not part of this change.
4. Review visit hours, conflicts, replacement dates, any previous revision coverage that will end, and remaining uncovered slots.
5. Choose **Approve and schedule**. Keep the admin in the same workspace and show the resulting coverage and visits.

Reuse the existing review-token and approval transaction. Preserve organization-first locking, active-worker/agency checks, eligibility, hours, uniqueness, cutoff rules, revision activation, retained history and in-app notifications. Recheck at confirmation. A phone agreement does not itself bypass availability or overtime limits. If the recorded availability is wrong, provide a contextual correction followed by a new review; an exception policy would require a separate decision.

Record who arranged the assignment, when and its origin separately from worker interest. Define who can read any internal note. Do not silently broadcast an internal phone note to workers. Preserve current notification behavior and distinguish in-app notice creation from proof that a worker received a phone push or email.

For this change, use an existing revision-linked open Care Request. Assigning an unpublished revision without posting is a separate product decision because posting currently advertises the request to workers.

## Consolidation priorities

1. **Client care setup:** intake → funding when applicable → weekly care → coverage, with the same client visible throughout. Retain save-and-return between steps rather than force a long wizard.
2. **Coverage:** reuse the existing embedded review for direct assignment, interested-worker selection and replacement. Keep Care requests as the agency-wide queue.
3. **Worker workspace:** expose Overview, Availability, Documents and Leave without requiring a large profile-edit form for daily operations. Keep personal details in Edit profile.
4. **Context preservation:** retain request filters, calendar date, selected slots and originating record after drawers close or actions finish. Prevent one overlay from hiding unsaved work in another.
5. **Role clarity:** dashboard/tower = next actions; Activity = past actions; Settings = account/agency administration. Test the apparent invitation overlap before changing it.

Keep Schedule as the cross-client calendar and Timesheets as the reporting surface. Combining every screen into one large page would make dense care records harder to use. Use small contextual panels for supporting information and retain full record pages for deeper work.

## Discussion and usability validation

### Focused client setup improvements (October 16, 2026)

The agreed intake → funding → weekly care → assignment → visits path now has explicit handoffs within the existing workspace:

- Intake shows a saved confirmation with **Continue setting up care** and **Back to clients**. The next destination uses the saved client's funding arrangement. Failed saves retain entered details, and the intake cannot be dismissed while saving.
- Funding saves offer **Continue to weekly care**. During a care draft, **Add funding** or **Amend funding** opens the existing authorization dialog. Saving or cancelling preserves the draft's date, weekdays, services and times. New funding starts with the draft's date; existing funding checks remain.
- Partial and full approval offer **View newly scheduled visits**, opening the first selected visit's week. A Saturday start with Monday care opens the following week. **This week** still returns to the current week. Intake, funding, revision saves and posting never create visits by themselves.

Local evidence: `tests/client-setup.browser.cjs` passed funded and self-pay journeys with fictional intercepted APIs, failed client/funding saves, cancelling an amendment, draft preservation, partial direct approval, first-visit navigation, and returning to a filtered directory. Existing client navigation and Care Requests browser suites passed. Both direct-assignment browser → real API → isolated PostgreSQL tests also passed. The full intake walkthrough verifies UI handoffs, not new backend rules. Build, type checks, focused lint and seven projection/date tests passed. CI includes the new setup walkthrough; hosted rollout and its first remote run remain pending.

### Agency walkthrough still needed
